### New finding that changes the code: the validator probe imports nothing from Hermes

`hermes plugins validate` imports `__init__.py` in a bare child interpreter and calls `register()` against a stub context (`hermes_cli/plugin_validate.py:200-330`). A top-level `from plugins.plugin_storage import plugin_data_dir` would fail there. **All Hermes imports go inside functions**, and `register()` must touch nothing but `ctx`.

The probe diffs only tools, hooks and middleware. CLI commands are recorded but not compared. So the manifest declares:

```yaml
provides_tools: []
provides_hooks: [post_llm_call]          # plus on_session_end if S1 needs it
provides_middleware: [tool_execution]
requires_env: []
```

*(As built in block C: the hooks are `pre_llm_call` and `post_llm_call`. `on_session_end` is not used; see S1 item 7.)*

## 2. Design decisions this plan makes

These are Claude's proposals. Grok should check them and the owner should approve them.

1. **Replay intercepts everything.** In replay mode the middleware never calls `next_call`. A hit returns the recorded string. A miss returns `{"error": "cassette miss: <tool> <args>"}` and marks the run diverged. *(Amended after Grok's S1 review: this holds for a claimed run. If the claim fails, tools run live and the run is marked INVALID; see decisions 6 and 9. The README says "offline for any run not marked INVALID".)* As a result:
   - the replay is offline by construction,
   - no approval prompt can ever come up, which meets rule 12 without `--yolo`, and *(Amended in block F: this holds for a claimed run. The child was `hermes -z`, which auto-approves dangerous commands, so an unclaimed run broke rule 12. The child is now `hermes chat -Q`, which denies them. See decision 5 and `docs/SECURITY.md`.)*
   - the README can say this plainly and back it with a test.
2. **Record only the allowlist.** `read_file`, `search_files`, `web_search`, `web_extract`, `skill_view`, `skills_list`, `session_search`. Other tools run live and are noted in the cassette as `unrecorded` (name only, no args or result), so the verdict can explain a later miss. *(Amended 2026-11-10, the owner: terminal is in, but narrowly. `terminal` is recorded only when the command is on a read-only list: `cat`, `type`, `dir`, `ls`, `rg`, `git log`, `git show`, `git diff`. It's keyed on the exact command string plus the working directory, and replayed only on an exact match. Anything else is a miss and never runs. When a record session runs a terminal command outside the list, saving the cassette prints a warning: "this cassette may not replay cleanly". The warning is never cut. Terminal replay is built in block C after the core replay works, and is the first thing cut if time runs short.)*
3. **The cassette key is the tool name plus canonical JSON of the normalised arguments.** Normalisation: `\` becomes `/`, the drive letter is lowercased, a relative path is resolved against the recorded working directory, keys are sorted, and default-valued arguments are dropped. For a key recorded more than once, replay returns the results in order and then repeats the last one. *(Amended: the cursor belongs to one replay binding, not to the cassette, so two runs never share it.)*
4. **Line ranges in `read_file`: v1 matches exact arguments only.** Recording the whole file would mean calling the tool with arguments the model didn't send, which changes what the model saw. Fallback, if Arete and the second model ask for different ranges in S2: on a `read_file` miss, look for a recording of the same path with no range and slice it. That's about 30 lines. Build it only if S2 shows the problem.
5. **`hermes cassette run` works from outside.** *(Amended in block F: the child is `hermes [--model=M] [--provider=P] [--skills=S] [--in=DIR] chat -Q --query=<request>`, not `hermes -z`. In 0.23.1 `-z` is an unattended turn that auto-approves dangerous commands; `chat -Q` is a finite single query whose unanswered approvals are denied by `approvals.single_query_mode: deny`. Its stdout is the gateway's redacted copy of the answer, and it prints `session_id:` on stderr, which must match the claiming session.)* It starts `hermes -z` as a child process with the recorded request, the chosen model or skill, and `--in <recorded cwd>`. It grades the child's final answer: from `post_llm_call` if the plugin captured it, otherwise from stdout. The cassette's recorded results are never changed by a run. Each run's verdict is written to `runs/<cassette>/<timestamp>.json`.
6. **Verdict.** *(Amended: INVALID is a fourth result and overrides the other three. It means the run can't be trusted to have been a replay: the arm was never claimed, an arm file was left over, or the claiming session's final answer doesn't match the child's stdout. An INVALID run is never PASS.)* PASS means every pin matched and there were zero misses. DIVERGED means one or more misses (shown even if the pins matched). FAIL means a pin was missing. If a run both missed and lost a pin, it shows FAIL plus a note of the miss count. A "path" column shows hits and misses and the call order compared with the recording. It never sets the colour. Pin matching ignores case, treats `\` and `/` as the same, and accepts `re:` for a regex pin.
7. **Storage.** One JSON file per cassette in `plugin_data_dir("session-cassettes")/cassettes/`. Writes go to a temporary file first and are then renamed into place (atomic). The file has a `format: 1` field.
8. **No third-party dependencies.** Standard library only. Output is a plain-text table with ANSI colour, which Windows Terminal supports, and turns off with `NO_COLOR`.
9. **Arm, claim and binding** (added after Grok's S1 review, `reviews/s1-mode-switching.md`; approved by the owner 2026-11-10).
   - **One run at a time.** `cassette run` takes a lock in the plugin data dir and refuses to start while another arm is waiting.
   - **Atomic claim.** `pre_llm_call` claims an arm only when `is_first_turn` is true, `platform == "cli"` and the request text matches. It claims by renaming `armed/<id>.json` to `claimed/<id>.json`. Only the session whose rename succeeds wins. *(Amended in block C: the claim is not a rename. On Windows the race test showed up to 3 of 8 threads being told their rename of one arm succeeded. The claim is now the exclusive creation (`O_EXCL`) of `claimed/<id>.json`; the winner then removes `armed/<id>.json`. The request text is compared after trimming outer whitespace and unifying line endings.)*
   - **Bind the turn, not the session.** The binding holds `session_id` plus `turn_id`. Only tool calls with that `turn_id` are recorded or replayed. During replay, any other `turn_id` on that session (the background-review fork shares the `session_id`) gets an error, never `next_call`, and it doesn't count as a miss. During record, those calls run live and aren't saved. The next `pre_llm_call` on that session replaces the binding, so nothing is released on `post_llm_call` or `on_session_end`.
   - **No mid-turn expiry.** The TTL only cleans up arms nobody claimed. A claimed binding never expires while its turn is running.
   - **Proof the claim was ours.** `post_llm_call` stores the bound turn's final answer. After the child exits, the parent compares it with the child's stdout. A match is a valid run. No match, no claim, or a leftover arm makes the run INVALID.
   - **Catch inside the callback.** The whole middleware callback sits in one `try`/`except Exception` that returns a `cassette miss` string. It never raises, because a raise runs the real tool.
   - **`@` references are refused at record time.** Hermes expands them before `pre_llm_call` sees the text, so they could never match an arm.
   - **Known gap, disclosed:** memory prefetch adds local memory to the replay turn without going through `tool_execution`. It reads local data and makes no network call. It's checked in block E and disclosed in the README.

## 6. Disclosures for the README and PR (rule 13)

- Cassettes store the full results of recorded tools: file contents, search hits, web extracts and session-search results. They are plain JSON under the plugin data folder. Anyone with the file sees that content.
- In replay mode no tool runs. Every tool call is answered from the cassette or refused with a `cassette miss` error. That includes tools that would normally ask for approval. Nothing is executed, so nothing is approved.
- `hermes cassette run` starts one `hermes chat -Q` child process with the model the user names. It uses no `--yolo`, no `-z` (which auto-approves) and changes no approval settings. *(Amended in block F; this line used to say `hermes -z`, which was wrong about approvals.)*
- If no session claims the run (for example, the gateway hasn't loaded the plugin), the turn runs **live**: Hermes denies flagged commands, but unflagged tools (plain `rm`, `write_file`, ...) run. The run is graded INVALID, but only after the child exits. Seen live in block F. A replay is offline only when its run is not INVALID.
- No network calls of its own, no telemetry, no judge model, no self-update. (If terminal replay stays: it records the output of a fixed list of read-only commands.)

## 8. Which Claude model and effort for each block

**The trade-off.** Fable 5.2 is the stronger model and costs about twice as much per token as Opus 5.5 ($8/$40 against $4/$20 per million input/output tokens). Its turns also run longer, often several minutes on a hard task, and against a 23-hour deadline that time matters as much as the money. Anthropic's guidance for Fable 5.2 is to start at `high` and go to `xhigh` only where it measurably helps. So use `xhigh` for the few places where a subtle mistake would sink reliability, not as the default.

**Rule of thumb.**
- **Fable 5.2 xhigh:** the outcome hinges on reasoning about behaviour you can't see directly, such as process boundaries, call order or rule compliance. A miss there costs hours or a rejected entry.
- **Opus 5.5 high:** normal feature code and writing with a clear spec.
- **Opus 5.5 medium:** mechanical work, such as running commands, boilerplate, fixtures and YAML.

| Block | Model and effort | Why |
|---|---|---|
| A: S1 mode spike | Opus high to build and run it. **Fable xhigh if the result is unclear** (e.g. the env var arrives in some processes and not others). | The spike is small. Reading an odd result across the gateway boundary is where depth pays. |
| A: S2 Arete calls, fixture repo | Opus medium | Building fixtures and reading logs. |
| B: `store.py`, `verdict.py` | Opus high | Clear spec. Path normalisation has edge cases, but the unit tests catch them. |
| C: middleware core | **Fable xhigh** | The heart of the plugin: the single-use `next_call`, record versus replay, the miss path, concurrent tool calls, and nothing ever leaking a live call during replay. A subtle bug here is the reliability score. |

**How to switch.**
- Change model and effort at a block boundary, not in the middle of a task. The prompt cache is per model, so switching mid-session rebuilds the context at full price.
- Start each Fable block in a fresh session that reads `AGENTS.md` and this plan. That keeps its long turns focused on one job.

**If time gets tight:** drop the Fable passes in this order: block E debugging, block G README audit, block A spike reading. Keep Fable for block C and the pre-freeze review in block H.

**Handoffs.** At the end of each block, Claude updates the Progress log below and then tells the owner three things: which model and effort to switch to, whether to `/clear`, and the one-line prompt for the new session. A fresh session reads `AGENTS.md`, this plan and the log, and nothing else.
